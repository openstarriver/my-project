我从 GitHub 上重新找了一份 PRD 模板往里填写。

**产品名称：** [自我介绍]

**问题陈述：** [需要登录页面+自我介绍+轮播图+AI留言板]

---

## 目标与成功标准

### 业务目标

1. 账号密码输入正确能跳转；错误留在登录界面并报错，登录状态刷新后能保持。
2. 允许注册新账号，若账号已注册则拦下。
3. 轮播图能自动播放。
4. 留言要能保存，刷新后仍存在，并且留有 AI 回复的痕迹；留言可删除，AI 回复失败时要给予反馈。

### 非目标（不在范围内）

- 不能实现 A 用户的留言内容出现在 B 的界面上。

## 产品需求

### 功能需求

1. **登录校验**
   - **描述：** 账号存于 localStorage（`zhangxianghang_credential`），去空格后与已注册账号逐一比对，全部匹配才放行。空值与不匹配分别给出提示，均不跳转。首次打开时账号存储为空，回落到内置账号 `123456 / 123456`。
   - **验收标准：**
     - [ ] 账号密码全部匹配时跳转到主站内容
     - [ ] 账号或密码不对时不跳转，并给出错误提示
     - [ ] 账号为空、密码为空分别有独立提示
     - [ ] 首次打开时可用内置账号 `123456 / 123456` 登录
   - **补充：** 原本账密存储在浏览器里，用开发者工具（DevTools）就能直接查到，不安全。如果要做到换设备、换浏览器仍能用原账号密码登录，可以把 localStorage 换成自己写的后端：找一台服务器，把账密存到服务器里；或者直接接入一个现成的后端服务（如 BaaS），这样更省事，账密也不会出现在前端代码里。

2. **注册新账号**
   - **描述：** 三道校验依次拦下 —— 账号密码非空 → 两次密码一致 → 账号不重复；通过后 `push` 追加（而非覆盖）已有账号并切回登录页。账号列表存在 localStorage 的 `zhangxianghang_credential` 键里。
   - **验收标准：**
     - [ ] 注册成功后新账号可以登录
     - [ ] 账号已存在时被拦下并提示
     - [ ] 两次密码不一致时被拦下并提示
     - [ ] 新账号是追加的，原有账号仍能登录
   - **补充：** 我觉得可以实现一个注册接口，这样能保证账密的安全：服务器能判断账号密码是否非空，也能判断注册的账号是否重复；但两次输入密码是否一致，只能交给前端去做。

3. **登录态保持与退出**
   - **描述：** 登录态单独存在 `zhangxianghang_loggedIn`，与账号数据分开存 —— 退出登录只清登录态，不影响已注册的账号。**必须在 `setup` 里就同步读一次**：留到 `onMounted` 再赋值，已登录用户的每次刷新都会先闪一下登录表单。
   - **验收标准：**
     - [ ] 登录后刷新页面仍是登录状态，不闪登录表单
     - [ ] 退出登录后回到登录页
     - [ ] 退出登录不影响已注册的账号，仍能重新登录

4. **自我介绍页**
   - **描述：** 展示头像、姓名、学校及若干信息项，全部收在 `introData` 一个对象里，模板只负责渲染；头像走 `public/` 绝对路径引用，构建时原样拷到网站根目录。
   - **验收标准：**
     - [ ] 展示头像、姓名、学校及其余信息项
     - [ ] 改资料只需动 `introData` 一处，不碰模板
     - [ ] 头像正常显示

5. **轮播图**
   - **描述：** 5 张幻灯片，1.5 秒自动切换，配左右按钮、底部指示点和「第 n / 5 张」计数。位移由计算属性驱动的 `transform` 实现，不手动操作 DOM。手动切换后**重置计时器**，重置前先清旧定时器，组件卸载时清掉定时器。
   - **验收标准：**
     - [ ] 自动播放，每 1.5 秒切换一张
     - [ ] 左右按钮可手动切换，指示点与「第 n / 5 张」计数同步
     - [ ] 手动切换后重新计时，观感上不会一次跳两张
     - [ ] 鼠标移入暂停、移出继续
     - [ ] 反复进出不会叠起多个定时器导致播放越来越快
   - **补充：**
     - 如果要让最后一张和第一张无缝衔接，我觉得可以由原来的 1 2 3 4 5 改成 1 2 3 4 5 1，保证第一张和最后一张完全一样。判断时，如果是前五张就滑到下一张；如果是第六张，就瞬移（把位置直接切回第一张），这样视觉上看不出来。
     - 使用现有组件库会省去很多麻烦，毕竟素材和 UI 都是准备好的，也不用担心 bug；但缺点是再改个性化就相对麻烦。

6. **留言持久化**
   - **描述：** 留言存 localStorage 键 `zhangxianghang_messages`，**先落盘再请求 AI**。
   - **验收标准：**
     - [ ] 提交后刷新页面，留言仍然存在
     - [ ] 最新一条显示在最上面
     - [ ] AI 请求失败时，留言本身刷新后依然存在
     - [ ] 刷新后不会永久卡在「正在思考…」
     - [ ] 同一毫秒内连发两条，id 不重复，删一条不会连带删掉另一条

7. **AI 自动回复**
   - **描述：** 留言提交后请求同站点内的 `/api/chat`，由 Vercel 服务端函数转发到上游大模型（当前为通义千问 `qwen-max`）。上游地址由环境变量 `BASE_URL` 提供，换模型只改环境变量，前端不动。系统提示词约束回复的语气与长度（50–150 字），前端按 `temperature 0.8`、`max_tokens 300` 请求。
   - **验收标准：**
     - [ ] 留言提交后自动生成并展示一条 AI 回复
     - [ ] 回复语气与长度符合系统提示词设定
     - [ ] 更换上游模型只需改环境变量，前端不动
   - **补充：**
     - 前端直接调上游会导致 API Key 写在前端页面，造成泄露，所以要走 Vercel 环境代理。收益是更安全、不会泄密；代价是多了一层代理，增加延迟，同时代码变复杂、维护难度上升。说实话，选 qwen-max 是因为有免费的 100 万 token 可以白嫖；但在现实中就要考虑多层因素：首先是成本——绝大部分回复都是询问答疑，基本不出现大工程的项目，所以没必要用特别高端、烧钱的大模型；其次要考虑延迟小一点，实在不行再加流式输出（后续细说）。回复质量我认为主要取决于给 AI 的提示词，以及对每条回复的 token 限制。
     - 若出现超时，不能直接把报错码反馈给用户（大多看不懂），要直接用「超时」「限流」「请稍后再试」这样的字样让用户看懂。

8. **AI 调用状态反馈**
   - **描述：** 请求中显示「正在思考…」+ 动画点，成功显示回复，失败显示可读的错误文案；上游的原始报错不直接透给访客。
   - **验收标准：**
     - [ ] 请求中显示「正在思考…」
     - [ ] 成功时显示 AI 回复
     - [ ] 失败时显示可读文案，不出现上游原始报错
     - [ ] 提交期间连按回车不会发出两条留言

### 遗留项

1. **AI 回复流式输出**
   - **描述：** 当前 `/api/chat` 一次性返回、前端整体渲染。改造需服务端函数改为流式转发，前端按增量追加渲染。**尚未实现**
   - **验收标准：**
     - [ ] AI 回复逐字增量出现，而不是等待后整体显示
   - **补充：**
     - 我认为流式输出解决的最主要问题，是延迟太长导致用户体验差。流式输出可以减少用户感知到的等待时间（虽然总时间没有减少），它改变的是回复呈现给你的节奏，其次才是动画 UI 效果的美化。但目前 qwen-max 基本能在 10 秒内完成回复，所以我认为目前没必要做流式输出，因此写进了遗留项。
     - 我会观察这个功能是否真的有必要、是否真的有相关需求，再决定是改文案还是改密，我觉得不能一概而论。

### 非功能需求

#### 安全与隐私

- **API Key 只存在服务端环境变量里，不下发到浏览器** —— 这是安全边界，不是可选项。
- 上游的原始报错不直接透给访客，只给状态码。

#### 可维护性

- 站点内容与模板分离：个人信息（`introData`）、幻灯片（`slides`）为独立常量，改内容不碰模板。
- AI 人格提示词集中在 `callQwenMax` 内，未散落在模板中。

#### 可部署性

- 一条命令上线：Vite 构建，Vercel 托管。

#### 浏览器/平台支持

- 响应式：有视口 meta，手机上可正常打开，地址栏不出现白边。

## 用户体验与设计

### 关键交互

1. **登录校验**
   - **触发条件：** 点击「登录」
   - **行为：** 账号去空格后与已注册账号逐一比对，任一不匹配即拦下
   - **反馈：** 账号为空、密码为空、不匹配分别给提示，均不跳转

2. **轮播图切换**
   - **触发条件：** 1.5 秒定时到点 / 点左右按钮 / 鼠标移入移出
   - **行为：** 计算属性驱动的 `transform` 位移；手动切换先清旧定时器再重置计时
   - **反馈：** 指示点与「第 n / 5 张」计数同步；移入暂停、移出继续

3. **留言提交**
   - **触发条件：** 点提交，或在输入框按回车
   - **行为：** 先写 localStorage，再请求 `/api/chat`；按钮置灰，函数入口再挡一道
   - **反馈：** 「正在思考…」→ AI 回复 / 可读的错误文案

4. **留言删除**
   - **触发条件：** 点删除
   - **行为：** 300ms 淡出动画后移除数据并同步存储
   - **反馈：** 留言从列表消失，刷新后不再出现

5. **退出登录**
   - **触发条件：** 点退出
   - **行为：** 只清 `zhangxianghang_loggedIn`，不动账号数据
   - **反馈：** 回到登录页，已注册账号仍可重新登录

## 技术规格

### 数据模型

| 键名 | 内容 | 字段 | 生命周期 |
| --- | --- | --- | --- |
| `zhangxianghang_credential` | 已注册账号数组 | `account`、`password` | 注册时追加；为空或损坏时回落内置账号 |
| `zhangxianghang_loggedIn` | 登录标记（字符串 `'true'`） | — | 登录成功写入，退出登录清除；删掉它不影响账号 |
| `zhangxianghang_messages` | 留言数组 | `id`、`name`、`content`、`time`、`aiReply` | 发表时写入，删除时移除|

- **AI 新增** 读取侧一律做容错：凭证额外校验每个元素都带账号密码字段，留言只校验顶层是数组，任何解析异常都降级为空列表 / 初始账号，不让一条脏数据把整页拖白。但需要留证据，否则不知道解析失败是不是因为脏数据，因此这条也作为遗留项。

- **补充：** 三个 key 必须分开写。如果放到一个函数里，那么我刷新或者重新登录时，就会把整个函数都调用一遍，容易误触导致所有留言全没了；而且分开写可维护性更好，修改时只要针对某一功能改就行。

## 开发记录

### 我踩的坑

#### 1. 把 Vue 当成一个「软件」

- **现象**：两个项目塞进同一个文件夹后集体报错，什么都打不开。
- **原因**：刚接触 Vue 时，我以为一个项目只有一个 `.vue` 文件，把 `App.vue` 当成所有项目的统一入口。
- **解决**：一遍遍问 AI，才理清 Vue 的项目 / 入口 / 组件三层关系。

#### 2. 挪了文件位置，没改引用路径

- **现象**：调整过目录结构后一片引用错误，怎么调都调不回来。
- **原因**：脚手架和 `App.vue` 都是 AI 搭的，我误以为文件放哪都行 —— 我改的是文件夹的存放顺序，`App.vue` 里的相对路径没跟着改。
- **解决**：全部删掉，从零重来一遍。**教训：动文件之前，先看清谁在引用它。**

#### 3. 密钥隐藏不能全交给 AI（两次翻车）

- **第一次**：让 Claude Code 手抄密钥，它抄漏了一位。控制台一直不报错，只有 AI 回复一直失败、那块区域是灰的。我一开始怀疑是 JS 代码的问题，一直在 Console 里调试：每段 JS 代码结尾都加一条 `console.log` 打印中间值，结果都没问题。后来在 AI 协助排查下，才想到可能是上游 API 的问题。于是发了一条留言，在 Network 面板里查看 `/api/chat` 的请求，响应返回 `Invalid API-key provided.`，范围一下缩小到密钥，这才发现密钥不完整。
- **第二次**：密钥其实已经藏在 Vercel 环境变量里，Claude Code 却断定我的密钥「完全泄露」，催我立刻更换并推荐一套「新方法」。争论半天它才承认两者是同一件事 —— 它把我另一个文件夹里未隐藏密钥的 HTML 版本当成了 Vue 版。
- **教训**：**AI 的结论要问依据，别被它的语气带走**；密钥这种事，自己确认一遍才作数。

#### 4. icon 图片「找得到、放不对」

- **现象**：让 AI 帮忙找图标，最后图片没出现在该出现的位置，项目里也搜不到文件。
- **解决**：自己找图、改尺寸，放进 `public/` 的指定位置。
